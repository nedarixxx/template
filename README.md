# Trip Service (Lab 01)

Сервис управления поездками платформы TripGo.

## Требования
- Go 1.22+
- PostgreSQL 16+
- tripgoctl
- make

## Быстрый старт

1. Поднять окружение:
tripgoctl environment start

2. Применить миграции:
make migrate

3. Собрать и запустить сервис:
make run

4. Запустить тесты:
make test

## Переменные окружения

| Переменная | Описание | Значение по умолчанию |
| --- | --- | --- |
| `HTTP_ADDR` | Адрес HTTP-сервера | `:8080` |
| `LOG_LEVEL` | Уровень логирования | `info` |
| `SHUTDOWN_TIMEOUT` | Таймаут graceful shutdown | `10s` |
| `DATABASE_URL` | Строка подключения к PostgreSQL | `postgres://tripgo:tripgo@localhost:21032/tripgo?sslmode=disable` |

## Принятые решения

### 1. Уровень изоляции транзакций

Выбран уровень изоляции **`Read Committed`** (стандартный для PostgreSQL).

* Атомарность создания записи в `trips` и статуса в `trip_status_history` полностью обеспечивается границами транзакции.
* Защита от конкурентного назначения двух поездок на одного водителя вынесена на уровень БД через частичный уникальный индекс. Более строгие уровни изоляции (`Repeatable Read` / `Serializable`) здесь избыточны и создавали бы лишние накладные расходы с ошибками сериализации.

### 2. Менеджер транзакций (TxManager)

* Реализован паттерн контекстного менеджера с методом `Do(ctx, fn)`.
* Репозиторий получает исполнителя через метод `GetExecutor(ctx)`: если в контексте уже открыта транзакция `pgx.Tx`, запрос идет через неё, если нет — напрямую через пул соединений `pgxpool.Pool`. Бизнес-код о `pgx` ничего не знает.
* Поддерживается вложенный вызов: если транзакция уже открыта, вложенный `Do` переиспользует текущую.
* Реализован перехват паники через `recover()`: при панике или ошибке транзакция гарантированно откатывается (`Rollback`), после чего паника пробрасывается дальше.

### 3. Запрет одновременных активных поездок

* В таблице `trips` добавлен частичный уникальный индекс:
```sql
CREATE UNIQUE INDEX trips_driver_active_idx ON trips (driver_id) WHERE (status = 'active');

```


* При параллельных запросах на одного водителя база выбрасывает ошибку с кодом `23505 (unique_violation)`. Репозиторий распознает её и преобразует в доменную ошибку `ErrDriverBusy`, отдавая клиенту `409 Conflict` (`driver_busy`).

### 4. Конкурентное завершение поездки

* Завершение реализовано атомарным запросом `UPDATE trips SET status = 'completed', finished_at = $1 WHERE id = $2 AND status = 'active'`.
* Если поездка уже завершена другим параллельным запросом, `RowsAffected == 0`. В этом случае выполняется дополнительное чтение, и клиенту возвращается `409 Conflict` (`trip_completed`).
