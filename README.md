# Trip Service (Lab 02)

Сервис управления поездками платформы TripGo. Реализован по принципам Clean Architecture с соблюдением строгой изоляции слоёв, транзакционной целостности и сквозной наблюдаемости (OpenTelemetry, JSON slog, Jaeger).

---

## Требования

* Go 1.27+ (или 1.24+)
* PostgreSQL 16+
* Docker & Docker Compose
* make / tripgoctl

---

## Быстрый старт

### Вариант 1. Запуск всего стека через Docker Compose

Запуск PostgreSQL, Jaeger и сервиса одной командой:

```bash
make up
# или docker compose up -d --build
```

* **HTTP API:** `http://localhost:8080`
* **Jaeger Web UI:** `http://localhost:22686`
* **PostgreSQL:** `localhost:22032` (логин: `tripgo`, пароль: `tripgo`, база: `tripgo`)

Остановка стека:

```bash
make down
```

### Вариант 2. Локальный запуск через окружение

1. Поднять окружение базы данных и трассировки:
   ```bash
   tripgoctl environment start
   ```

2. Применить миграции базы данных:
   ```bash
   make migrate
   ```

3. Собрать и запустить сервис:
   ```bash
   make run
   ```

## Эндпоинты сервиса

### Бизнес-API

* `POST /api/v1/trips` — создание поездки (возвращает `201 Created` или `409 Conflict`, если водитель занят).
* `GET /api/v1/trips/{tripId}` — получение информации о поездке (`200 OK` или `404 Not Found`).
* `POST /api/v1/trips/{tripId}/finish` — завершение поездки (`200 OK` или `409 Conflict`, если поездка уже завершена).

### Пробы работоспособности (Health Checks)

* `GET /health` — **Liveness probe**: проверка жизнеспособности процесса (возвращает `200 OK` с телом `{"status":"ok"}`).
* `GET /ready` — **Readiness probe**: проверка готовности сервиса обрабатывать трафик (выполняет ping к PostgreSQL, возвращает `200 OK` или `503 Service Unavailable`).

## Архитектура проекта

Проект организован по правилам Clean Architecture с контролем направлений зависимостей через линтер `depguard`:

* `internal/domain/trip` — ядро бизнес-логики: сущности, доменные инварианты, статусы и ошибки (покрытие тестами **100.0%**). Не зависит от внешних слоёв.
* `internal/usecase/trip/...` — сценарии использования (`create`, `get`, `finish`) и оркестрация бизнес-логики (покрытие тестами **100.0%**). Зависит только от домена и интерфейсов хранилища.
* `internal/http/trip/...` — транспортный уровень Chi: маршрутизация, валидация DTO, инкремент метрик и маппинг ошибок в формат RFC 7807 Problem Details (покрытие тестами **100.0%**).
* `internal/repository/trip` — персистентность данных в PostgreSQL на базе `pgxpool` и драйвера `otelpgx` (покрытие тестами **78.5%**).
* `internal/infra/telemetry` — сквозная трассировка OpenTelemetry, сбор метрик и структурированное JSON-логирование `slog` с обогащением контекста `trace_id` и `span_id`.

## Принятые решения (Лабораторная работа 02: Наблюдаемость и развёртывание)

### 1. Структурированное логирование (slog + Middleware)

* Использован стандартный пакет `log/slog` с выводом в формате JSON (`slog.NewJSONHandler`).
* Реализован кастомный обработчик `traceHandler`, который перехватывает записи логов и извлекает текущие `trace_id` и `span_id` из OpenTelemetry span context (W3C standard), автоматически обогащая каждую строку лога.
* Middleware `Logging` фиксирует каждый завершённый запрос с атрибутами:
  * `method` (HTTP метод)
  * `route` (шаблон маршрута, например `/api/v1/trips/{tripId}`)
  * `status` (код ответа)
  * `duration_ms` (длительность обработки в миллисекундах)

### 2. Распределённая трассировка (OpenTelemetry + Jaeger)

* Инициализирован глобальный `TracerProvider` с OTLP gRPC экспортером (`go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc`), передающим данные в Jaeger (порт `22317` / `4317`).
* Входящие HTTP-запросы обогащаются спанами через middleware `Tracing`, поддерживающее распространение контекста по заголовку `traceparent`.
* Запросы к PostgreSQL трассируются драйвером `otelpgx`: вызовы `BeginTx`, `QueryRow`, `Exec`, `Commit` и `Rollback` создают дочерние спаны, позволяющие детально анализировать задержки на уровне СУБД в веб-интерфейсе Jaeger.

### 3. Сбор метрик (OpenTelemetry Metrics)

* Зарегистрирован `MeterProvider` с бизнес-счётчиками:
  * `trips_created_total` — инкрементируется при успешном создании поездки (`201 Created`).
  * `trips_completed_total` — инкрементируется при успешном завершении поездки (`200 OK`).
* Для передачи метрик в хендлеры применён паттерн функциональных опций (`WithCounter(...)`), что позволило изолировать тесты с использованием no-op провайдеров (`noop.NewMeterProvider`) без побочных эффектов.

### 4. Пробы готовности и жизнеспособности (Liveness & Readiness)

* `/health` возвращает статус `200 OK` при работающем процессе сервера.
* `/ready` выполняет реальный `Ping(ctx)` к пулу базы данных PostgreSQL (`pgxpool.Pool`). Если база недоступна или пул перегружен, эндпоинт возвращает ошибку `503 Service Unavailable`, предотвращая маршрутизацию трафика на неисправный под.

### 5. Graceful Shutdown

* Сервис слушает системные сигналы завершения `SIGINT` и `SIGTERM`.
* При получении сигнала инициируется graceful shutdown HTTP-сервера с таймаутом `SHUTDOWN_TIMEOUT` (10 секунд):
  * Прекращается приём новых входящих соединений.
  * Дожидается завершение всех активных запросов.
  * Корректно закрывается пул соединений PostgreSQL (`pool.Close()`).
  * Сбрасываются буферы телеметрии в Jaeger (`telemetry.Close()`).

### 6. Контейнеризация и оркестрация (Docker & Compose)

* Написан оптимизированный multi-stage `Dockerfile`:
  * **Stage 1 (Builder):** сборка бинарника на базе `golang:1.27-alpine` с флагами оптимизации размера `-ldflags="-s -w"` и отключённым CGO (`CGO_ENABLED=0`).
  * **Stage 2 (Runtime):** минимальный образ `alpine:3.20` с установленными CA-сертификатами и временными зонами.
  * Безопасность: запуск от имени непривилегированного пользователя `appuser`. Итоговый вес образа составляет всего **44.7 MB**.
* Создан `docker-compose.yml`, объединяющий базу данных PostgreSQL (с проверкой `healthcheck`), трассировщик Jaeger и сам сервис `trip-service`.

## Архитектурные решения (Лабораторная работа 01)

### 1. Уровень изоляции транзакций

Выбран уровень изоляции **`Read Committed`** (стандартный для PostgreSQL).

* Атомарность создания записи в таблице `trips` и соответствующего события в таблице аудита `trip_status_history` полностью обеспечивается границами транзакции.
* Защита от конкурентного назначения двух поездок на одного водителя вынесена на уровень СУБД через частичный уникальный индекс. Более строгие уровни изоляции (`Repeatable Read` / `Serializable`) здесь избыточны и привели бы к неоправданным накладным расходам и частым ошибкам сериализации (`could not serialize access`).

### 2. Менеджер транзакций (TxManager)

* Реализован паттерн контекстного менеджера с методом `Do(ctx, fn)`.
* Репозиторий получает исполнителя запроса через метод `GetExecutor(ctx)`: если в контексте уже открыта транзакция `pgx.Tx`, запрос выполняется внутри неё; если транзакции нет — напрямую через пул соединений `pgxpool.Pool`. Бизнес-код сценариев абстрагирован от типов драйвера `pgx`.
* Поддерживается вложенный вызов: если транзакция уже открыта, внутренний вызов `Do` прозрачно переиспользует текущую транзакцию.
* Реализован безопасный перехват паники через `recover()`: при панике или ошибке транзакция гарантированно откатывается (`Rollback`), после чего паника пробрасывается дальше. Обязательный сценарий отката проверен интеграционным тестом `TestTransaction_RollbackOnFailure`.

### 3. Запрет одновременных активных поездок

* В таблице `trips` создан частичный уникальный индекс:
  ```sql
  CREATE UNIQUE INDEX trips_driver_active_idx ON trips (driver_id) WHERE (status = 'active');
  ```
* При параллельных запросах на создание поездки для одного водителя СУБД атомарно отклоняет второй запрос с кодом ошибки `23505 (unique_violation)`. Репозиторий перехватывает её и преобразует в доменную ошибку `ErrDriverBusy`, отдавая клиенту HTTP-ответ `409 Conflict` (`driver_busy`).

### 4. Конкурентное завершение поездки

* Завершение выполняется атомарным SQL-запросом:
  ```sql
  UPDATE trips 
  SET status = 'completed', finished_at = $1, updated_at = $1 
  WHERE id = $2 AND status = 'active';
  ```
* Если поездка уже завершена другим параллельным запросом, условие `WHERE status = 'active'` не срабатывает и `RowsAffected == 0`. В этом случае выполняется дополнительное чтение:
  * Если запись существует в статусе `completed`, клиенту возвращается `409 Conflict` (`trip_completed`).
  * Если запись с данным ID отсутствует в базе, возвращается `404 Not Found` (`trip_not_found`).
